# Архитектура

Документ объясняет, *почему* проект устроен именно так, и как он масштабируется на
сценарии за пределами исходного ТЗ. Цель проектирования — чтобы команда из многих
разработчиков добавляла юнитов, действия и механики, **не редактируя `Core/` и не
конфликтуя друг с другом**.

## Две несущие идеи

**1. Юнит — это данные + поведение, и то и другое декларативно.**

- *Что юнит есть* — структура `UnitTraits` (HP/нет, скорость, занимает ли клетку,
  уязвимость к ближнему/дальнему бою, модификатор дистанции). Это «физика» юнита.
- *Что юнит делает* — упорядоченный список объектов `IAction`. Ход = «выполнить
  первое подходящее действие».

**2. `Core` знает только абстракции.** Он оперирует `Unit`, `IAction`, `Map`,
никогда — конкретным типом юнита. Ни одного `if (type == Swordsman)` во всём движке.

## Слои и зависимости

```
        +-------------------+        +--------------------------+
        |       main        |        |          tests           |
        | (регистрация спавн |        | (харнесс без зависимостей)|
        |  команд → юниты)   |        +-----------+--------------+
        +---------+---------+                     |
                  |                               |
                  v                               v
   +--------------+-------------------------------+--------------+
   |                          Core                               |
   |   Unit · IAction · TurnContext · Map · Rng · Simulation     |
   +------+--------------------------------+---------------------+
          ^                                ^
          |                                |
   +------+---------+              +--------+---------+
   |    Features    |              |        IO        |
   | юниты + Actions |  --emit-->   | Commands · Events |
   +----------------+              +------------------+

Стрелки — направление зависимостей. Features зависит от Core и эмитит события IO.
Core НЕ зависит ни от Features, ни от конкретных команд.
```

## Поток одного хода

```
Simulation.run():
  пока юнитов >= 2:
    snapshot = текущие юниты (порядок создания)   # фиксируем, кто ходит в этом тике
    для каждого unit из snapshot:
        unit.act(ctx):                            # ctx = {Map, Rng, EventLog, tick}
            для каждого action из unit.actions:
                если action.perform(unit, ctx):   # первое сработавшее — ход потрачен
                    -> true (юнит что-то сделал)
    убрать мёртвых + эмитить UNIT_DIED            # мёртвый в этом тике уже сходил
    если за тик никто не сходил: стоп
```

Снэпшот в начале тика реализует правило ТЗ «юнит при HP ≤ 0 доигрывает текущий ход».
Поведенческие события (`UNIT_ATTACKED`, `UNIT_MOVED`, `UNIT_HEALED`) эмитят сами
действия; события жизненного цикла (`MAP_CREATED`, `UNIT_SPAWNED`, `MARCH_STARTED`,
`UNIT_DIED`) — `Simulation`.

## Почему так, а не «виртуальный `act()` на каждого юнита»

Наивный подход — у каждого юнита свой `act()` с зашитой логикой — приводит ровно к
тому, за что завернули прошлую версию: ближний бой копируется в каждого, кто умеет
бить; добавление летающего/безжизненного юнита требует правок в общем коде движка.

Композиция действий устраняет это:

| Юнит      | Состав (всё — в конструкторе, `Features/`)                                   |
|-----------|------------------------------------------------------------------------------|
| Swordsman | `MeleeAttack(str)` → `MoveToTarget`                                          |
| Hunter    | `RangedAttack(agi, 2..R, clearMelee)` → `MeleeAttack(str)` → `MoveToTarget`  |
| Tower     | `RangedAttack(pow, 2..5, !clearMelee)`                                       |
| Healer    | `Heal(spirit, r2)` → `MoveToTarget`                                          |
| Crow      | `MeleeAttack(agi)` → `MoveToTarget`  (+ traits: flying)                      |
| Mine      | `ExplodeIfEnemyNear(pow, r2, r3)`    (+ traits: no HP, untargetable)         |

Логика ближнего боя существует **в одном** классе `MeleeAttack` и переиспользуется
тремя юнитами. То же для дальней атаки и движения.

## Разделение ответственности (что критиковали в `Map`)

- **`Map`** — только пространственное состояние: кто где, что рядом, куда шагнуть.
  Возвращает «сырые» наборы юнитов; **боевые правила в неё не просачиваются**.
- **`Rng`** — отдельный инжектируемый источник случайности.
- **`Simulation`** — цикл и события жизненного цикла.
- **Действия** — поведение и его события.

Это делает каждую часть тестируемой по отдельности (см. `tests/`): `Map` проверяется
геометрией, действия — на собранном вручную `TurnContext`, цикл — end-to-end с
перехватом вывода в `std::ostringstream`.

## Масштабирование за пределы четырёх плановых юнитов

Архитектуру проектировал не под конкретную четвёрку, а под классы изменений. Куда что
ляжет:

- **Новая характеристика** (брони, крит, сопротивление стихии) → поле в `UnitTraits`
  и учёт в соответствующем действии. `Core`-цикл не трогается.
- **Новое действие/механика** (рывок, призыв, аура, щит) → новый класс `IAction` в
  `Features/Actions/`. Юниты подключают его строкой `addAction<...>`.
- **Несколько действий за ход** (например, «двигайся И стреляй») → сейчас ход = первое
  сработавшее действие; модель расширяется политикой выполнения (`ActionPolicy`:
  `FirstThatActs` по умолчанию / `AllThatCan`), задаваемой на юните. Это локальное
  изменение `Unit::act`, не ломающее существующих юнитов.
- **Эффекты во времени** (яд, регенерация, оглушение) → список «эффектов» на `Unit`,
  тикающих в начале хода; каждый эффект — тоже маленький объект-стратегия. Естественно
  ложится на ту же модель композиции.
- **Команды и фракции** → поле `teamId` в `UnitTraits` + фильтр «свой/чужой» в выборе
  целей внутри действий. Запросы `Map` остаются нейтральными.
- **Площадные/цепные эффекты** → уже поддержаны (взрыв Мины бьёт всех в радиусе через
  `unitsInRange`), новый паттерн переиспользуется.
- **Детерминизм и воспроизводимость багов** → флаг `--seed`; тот же сид в тестах.
- **Производительность при тысячах юнитов** → линейные запросы в `Map` заменяются на
  пространственный индекс (равномерная сетка/хэш по клеткам) за тем же интерфейсом
  `Map`; вызывающий код не меняется. Сознательно не делал — ТЗ просит не думать о
  производительности, а преждевременная оптимизация усложнила бы чтение.

Общий принцип: **точки расширения — это данные (`UnitTraits`) и стратегии (`IAction`),
а не ветвления в движке.** Если новая фича требует трогать `Core` — значит, не хватает
обобщённого крючка, и чинить надо его, а не добавлять ветку под конкретный юнит.
