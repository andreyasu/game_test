# sw-battle-test

[![CI](https://github.com/andreyasu/game_test/actions/workflows/ci.yml/badge.svg)](https://github.com/andreyasu/game_test/actions/workflows/ci.yml)

Пошаговая симуляция боевых столкновений юнитов на сетке W×H.

Дополнительно: **[ARCHITECTURE.md](ARCHITECTURE.md)** — рациональ дизайна и стратегия
расширения · **[CONTRIBUTING.md](CONTRIBUTING.md)** — как добавлять юнитов и механики ·
**[KNOWN_ISSUES.md](KNOWN_ISSUES.md)** — допущения.

## Сборка и запуск

```bash
cmake -S . -B build
cmake --build build
./build/sw_battle_test commands_example.txt
```

Требования: компилятор с C++20 (clang 15+ / gcc 11+), CMake 3.16+, Ubuntu.

Для воспроизводимого прогона при отладке можно зафиксировать генератор случайных
чисел: `./build/sw_battle_test --seed 42 commands_example.txt`. Без флага симуляция
недетерминирована, как и допускает задание.

## Тесты и качество

```bash
ctest --test-dir build --output-on-failure   # 23 теста: Position, Map, Unit, бой, симуляция
```

Тесты написаны на маленьком собственном харнессе (`tests/TestFramework.hpp`) — **без
сторонних зависимостей**, как требует ТЗ. CI (GitHub Actions) на каждый push собирает
проект на **gcc и clang** с предупреждениями-как-ошибками (`-Werror`), гоняет тесты и
проверяет форматирование (`clang-format`).

## Формат сценария

```
CREATE_MAP 10 10
SPAWN_SWORDSMAN 1 0 0 5 2       # id x y hp strength
SPAWN_HUNTER    2 9 0 10 5 1 4  # id x y hp agility strength range
MARCH 1 9 0                     # unitId targetX targetY
```

Строки, начинающиеся с `//`, и пустые строки игнорируются.

## Архитектура

Главная цель проекта — расширяемость: новые юниты, действия и характеристики должны
добавляться **не трогая код в `Core/`**. Достигается это двумя идеями:

> **Юнит = декларативные характеристики (`UnitTraits`) + упорядоченный список
> переиспользуемых действий (`IAction`).**

```
src/
├── Core/        — фреймворк. Не зависит ни от одного конкретного юнита.
│   ├── Position       — клетка + дистанция Чебышёва
│   ├── Unit           — базовый юнит: id, позиция, HP, traits, список действий
│   ├── IAction        — интерфейс одного действия в ход юнита (точка расширения)
│   ├── TurnContext    — что доступно действию в ход (Map, Rng, EventLog, tick)
│   ├── Map            — пространственное состояние и запросы (только это)
│   ├── Rng            — источник случайности
│   └── Simulation     — цикл симуляции и события жизненного цикла
├── Features/    — конкретные юниты и переиспользуемые действия (сюда добавлять новое)
│   ├── Actions/       — MeleeAttack, RangedAttack, Heal, MoveToTarget, Explode…
│   ├── Swordsman, Hunter, …
└── IO/          — парсер команд и вывод событий (трогать для новых команд/событий)
```

### Поведение через композицию действий

Ход юнита — это «перебрать свои действия по порядку и выполнить первое подходящее».
Действие возвращает `true`, если оно отработало (и ход потрачен), иначе пробуется
следующее. Это убирает дублирование (логика ближнего боя, дальней атаки, движения
живёт в одном месте) и делает каждого юнита декларативным:

```cpp
Swordsman::Swordsman(...) : Unit(id, "Swordsman", pos, {.hp = hp})
{
    addAction<MeleeAttack>(strength);   // 1. Сокрушающий удар
    addAction<MoveToTarget>();          // 2. иначе — движется
}

Hunter::Hunter(...) : Unit(id, "Hunter", pos, {.hp = hp})
{
    addAction<RangedAttack>(agility, 2, range, /*requireClearMelee=*/true);  // Стремительный выстрел
    addAction<MeleeAttack>(strength);                                        // Удар из тени
    addAction<MoveToTarget>();                                               // иначе — движется
}
```

### Характеристики как данные

Физическая природа юнита описывается структурой `UnitTraits` (designated initializers),
а не зашита в логику. Сервисы `Core` читают эти поля и **никогда не делают `switch` по
типу юнита**:

| Поле                       | Зачем                                                       |
|----------------------------|-------------------------------------------------------------|
| `hp` (`optional`)          | `nullopt` — у юнита нет здоровья вообще (Мина)               |
| `movementSpeed`            | клеток за ход; `0` — статичный                              |
| `occupiesCell`             | занимает ли клетку (летающие/мины — нет)                    |
| `meleeTargetable`          | можно ли бить в ближнем бою                                 |
| `rangedTargetable`         | можно ли бить в дальнем бою                                 |
| `rangedDistanceReduction`  | на сколько сжимается дистанция стрелка по этому юниту        |

### Разделение ответственности

- **`Map`** отвечает ровно за одно: «кто где стоит и что находится рядом с точкой».
  Она НЕ логирует события, НЕ владеет RNG и НЕ исполняет march-логику. Запросы
  возвращают «сырые» наборы юнитов; боевые правила (кого можно бить, модификаторы
  дистанции) живут в действиях, поэтому `Map` ничего не знает об атаках и лечении.
- **`Rng`** — отдельный инжектируемый источник случайности.
- **`Simulation`** — цикл ходов и события *жизненного цикла* (`MAP_CREATED`,
  `UNIT_SPAWNED`, `MARCH_STARTED`, `UNIT_DIED`).
- **Действия** эмитируют *поведенческие* события (атака → `UNIT_ATTACKED`,
  движение → `UNIT_MOVED`, лечение → `UNIT_HEALED`).

### Как добавить нового юнита (Core не трогается)

1. `Features/MyUnit.{hpp,cpp}` — отнаследоваться от `Unit`, в конструкторе задать
   `UnitTraits` и собрать список действий из готовых `Actions/` (или написать новое
   действие, если механика принципиально новая).
2. `IO/Commands/SpawnMyUnit.hpp` — описать команду по аналогии с `SpawnSwordsman.hpp`.
3. В `main.cpp` — одна строка `parser.add<io::SpawnMyUnit>(...)`.

### Цикл симуляции

- Тик 1 — обработка команд (`MAP_CREATED`, `UNIT_SPAWNED`, `MARCH_STARTED`).
- Тик 2+ — юниты ходят в порядке создания; в конце тика мёртвые удаляются.
- Юнит, получивший смертельный урон, успевает сходить в текущем тике.
- Завершение: осталось меньше двух юнитов, или за целый тик никто не смог сходить.

### Дистанция

Метрика Чебышёва `max(|dx|, |dy|)` — естественна для 8-направленной сетки:
диагональный шаг стоит столько же, сколько прямой. Все запросы (движение, радиусы
атак, радиус взрыва) используют одну и ту же метрику.

## Юниты из плана расширения — реализованы

Все четыре юнита из исходного ТЗ добавлены как доказательство расширяемости —
**без единого изменения в `Core/`** (см. историю git: второй коммит трогает только
`Features/`, `IO/` и `main.cpp`). Каждый выражен через `UnitTraits` + композицию
действий:

| Юнит    | Команда                          | Чем выражен                                                        |
|---------|----------------------------------|--------------------------------------------------------------------|
| Башня   | `SPAWN_TOWER I X Y HP POWER`      | `speed=0` + `RangedAttack(power, 2, 5, requireClearMelee=false)`   |
| Лекарь  | `SPAWN_HEALER I X Y HP SPIRIT`    | `Heal(spirit, 2)` + `MoveToTarget`                                 |
| Ворон   | `SPAWN_CROW I X Y HP AGILITY`     | `speed=2`, не занимает клетку, melee-иммунитет, range −1; `MeleeAttack(agility)` + `MoveToTarget` |
| Мина    | `SPAWN_MINE I X Y POWER`          | `hp=nullopt`, не атакуется, не занимает клетку; `ExplodeIfEnemyNear(power, 2, 3)` |

Лекарь добавляет новое событие `UNIT_HEALED`; взрыв Мины переиспользует
`UNIT_ATTACKED` (атакующий — Мина). Демонстрационный сценарий: `scenarios_showcase.txt`.
